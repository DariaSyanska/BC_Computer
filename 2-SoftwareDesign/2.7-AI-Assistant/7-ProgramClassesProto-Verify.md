## 2. Технічна якість діаграми

### 2.1. Типізація та Інкапсуляція
- **Модифікатори доступу**: Всі класи правильно використовують `-` для атрибутів та `+` для методів.
- **Типи даних**: Типи вказані для всіх полів (Integer, String, Date, List) та результатів методів (void, String, Integer, Float).
- **Зауваження**: У класі `Chapter` метод `updateWordCount()` має бути `void` (вказано правильно), але варто уточнити, чи не повинен він приймати параметри.

### 2.2. Аналіз зв'язків
- **Композиція**: `CreativeProject` *-- `Chapter` — правильно, оскільки розділ не існує поза проєктом.
- **Залежність**: `CreativePlan ..> HealthData` — доречно для методу `adjustGoal(stressLevel)`.
- **Множинність**: 
    - `Writer 1 -- 1 CreativePlan` — вірно (один поточний план).
    - `Writer 1 -- 0..* HealthData` — вірно (історія записів).

## 3. Виявлені невідповідності та помилки

1. **Відсутність актора "Адміністратор"**:
    - На діаграмі UseCase (`1-UseCase.puml`) присутній актор `Admin`, проте в програмних класах він не відображений. 
    - Потрібно додати клас `Administrator` або методи для управління `LaborSafetyManual` та критеріями `Award`.

2. **Неповне покриття UC-2 та UC-6 (рекомендованого)**:
    - Відсутня логіка для FR2.1 (таймер роботи) та FR2.2 (тригери сповіщень).

3. **Логічне дублювання**:
    - Метод `saveDraft()` присутній і у `Writer`, і у `Chapter`. Варто уточнити: `Writer.saveDraft(project: CreativeProject)` або залишити лише на рівні сутностей контенту.

4. **Відсутність концептуальної моделі**:
    - Файл `2-SoftwareDesign/2.1-ConceptModel/UML-ConceptClasses.puml` відсутній у репозиторії, що унеможливлює повну перевірку відповідності програмних класів концептуальним сутностям.

## 4. Висновок та рекомендації

Прототип програмних класів загалом відповідає бізнес-логіці в частині творчої роботи та моніторингу здоров'я, але потребує доопрацювання допоміжного функціоналу.

**Рекомендації**:
1. Додати клас `NotificationManager` або подібний для реалізації вимог FR2.1 та FR2.2.
2. Додати клас `Administrator` для синхронізації з UseCase-діаграмою.
3. Додати в клас `Award` атрибут `criteria: String` або зв'язок з класом, що визначає умови отримання.
4. Синхронізувати методи збереження чернеток для уникнення неоднозначності.
